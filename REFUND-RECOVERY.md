# Refund recovery

CampTix receives refund success only after a positive reversal amount, refund reference and payout status TS. FAILED, PENDING, missing or unknown payout states return refund failure, persist `_shashura_refund_hold` on the order's first attendee, and alert the site administrator. An order lock prevents concurrent refund calls. An existing hold blocks subsequent full and partial refund calls before HTTP. This avoids repeating a successful ledger reversal when the phone payout has failed.

A transport error or process crash is ambiguous and also leaves a hold. Inspect the gateway dashboard using the original transaction and refund references. If reversal succeeded, recover ONLY the payout there. Do not click refund again or delete the hold to retry a payout. After independently confirming the customer's receipt, reconcile the CampTix accounting/status manually with the organiser. Pending payouts are not polled automatically because no payout enquiry/retry contract has been verified. Resolve the hold only through a controlled maintenance process after confirming accounting and delivery; this change does not provide a recovery UI.

This deliberately conservative patch requires review with the gateway and CampTix maintainers before deployment. A durable operation id plus server-side idempotency is still needed to automate safe retries after crashes, including a crash after successful payout but before CampTix records the result. The gateway must clarify fee/principal behavior before promising the full original charged amount is returned. Test full, partial and refund-all paths against pinned CampTix in sandbox with mocked responses; no production secrets or live payouts.
